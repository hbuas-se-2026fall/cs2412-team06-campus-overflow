# ADR-010：声誉异步结算与事件幂等

**状态**：已接受 ｜ **驱动特征**：正确性、可扩展性 ｜ **相关场景**：R-2、R-3、R-4、FF-8

## 背景

Q&A 上下文产生投票、采纳、回答提交、教师认证等领域事件后，声誉模块需要据此加减分、发徽章、结算悬赏、更新排行榜。这些操作如果和 Q&A 的主写操作在同一个事务里同步完成，会带来三个问题：

1. **耦合**：Q&A 事务直接依赖 Reputation 的表，Reputation 挂了会导致"采纳回答"这个核心操作也失败，而实际上用户并不会在意"回答被采纳"这个动作本身成没成功——声誉只是附加收益。
2. **重复风险**：OutboxRelay 的投递语义是"至少一次"（见 ADR-002），网络重试或进程重启会导致同一个事件被消费多次；如果声誉直接做 `reputation += 15`，重复一次就多给 15 分。
3. **跨模块原子性**：悬赏结算要同时改发起人的冻结积分、回答者的声誉、悬赏状态，这三步要么全做要么全不做，不能半路失败导致钱扣了但分没加。

## 决策

声誉模块采用**事件驱动 + 幂等消费**模式：

1. **异步消费**：ReputationEventHandlers 监听上游事件，每个处理器运行在自己的事务中；Q&A 主事务只负责把事件写入 outbox，不关心声誉结果。
2. **记账幂等**：所有声誉变动必须经过 ReputationLedgerService.record()，先查 `(event_id, user_id, reason)` 唯一键是否已存在，存在则直接返回 false（重复事件忽略）；不存在才写流水 + 更新账户余额。
3. **投影幂等**：搜索索引、通知、排行榜这些"读模型"投影使用 `processed_event` 表记录已处理事件，重复事件直接跳过。
4. **悬赏结算**：采纳事件触发时，BountyService.settleOnAccept() 先查该问题有没有 OPEN 状态的悬赏，没有就直接返回（幂等）；有则在同一事务里完成 award → spendFrozen → ledgerService.record() → 发 BountyAwardedEvent。
5. **徽章幂等**：BadgeService.grant() 先查该用户是否已持有该徽章，已持有则忽略，不重复发奖。
6. **定时对账**：每天跑一次 ReconciliationService.reconcile()，比对"账户余额 = 流水之和"，不一致数量以指标暴露（FF-8）。

## 后果

- 正面：
  - Q&A 主流程不被声誉拖慢，下游故障不影响用户核心操作；
  - 同一个事件投递多少次都不会重复加分，对账兜底保证余额正确；
  - 未来要加新的声誉规则（比如连续签到加分），只需新增事件处理器，不改 Q&A 代码。
- 负面：
  - 声誉更新有数百毫秒延迟（演示时赞了一下，排行榜可能要等一秒才变）；
  - 多了 ledger、processed_event、outbox 三张表和一个对账定时任务；
  - 出问题时排查链路长（要先看 outbox 有没有投递，再看 ledger 有没有记账）。

## 被否决的替代方案

- **同步在 Q&A 事务里直接改声誉**：耦合最高，Reputation 数据库抖动会导致"采纳回答"操作失败，且无法应对至少一次投递语义。
- **用 Redis 分布式锁防重复**：引入额外组件，且锁超时/死锁问题多；数据库唯一键已经能在并发下兜底，不需要分布式锁。
- **消费端不做幂等，靠 outbox 恰好一次投递**：恰好一次在分布式系统里成本极高，且网络重试无法完全避免，不如消费端幂等简单可靠。
