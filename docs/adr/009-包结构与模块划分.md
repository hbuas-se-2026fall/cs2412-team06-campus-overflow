# ADR-009：后端 Maven 多模块分包结构

**状态**：已接受 ｜ **驱动特征**：边界清晰、可独立测试、符合 DDD 教学目标 ｜ **相关场景**：Lab4 后端工程骨架

## 背景
课程要求按 DDD 限界上下文做物理分包，而不是传统的 controller/service/dao 技术分层。团队 5 人协作、16 周迭代，需要让每个人的代码改动尽量收敛在自己模块内，减少 merge 冲突；同时领域层必须能在不启动 Spring 容器的情况下跑单元测试。

## 决策
### 顶层模块（按限界上下文划分，共 6 个）
```
backend/
├── co-bootstrap/        # 启动入口，装配各上下文，main 方法所在
├── co-shared-kernel/    # 共享内核：Guard、异常、PageRequest、EventIds、Actor/Role
├── co-identity/         # 身份与认证上下文
├── co-qa/               # 问题与回答上下文（龙 + 何主责）
├── co-reputation/       # 声誉与激励上下文
└── co-discovery/        # 内容发现与通知上下文
```

### 每个限界上下文内部再分 5 个子模块（以 co-qa 为例）
```
co-qa/
├── co-qa-api/               # 对外发布契约：事件 record、跨上下文查询接口（允许别模块依赖）
├── co-qa-domain/            # 纯 Java 领域层：聚合根、实体、值对象、领域服务、仓储接口
├── co-qa-application/      # 应用层：CommandService/QueryService、端口接口（port）
├── co-qa-infrastructure/     # 基础设施：JPA 实体与仓储适配器、Redis 缓存、JDBC 读模型、Markdown 渲染
└── co-qa-interfaces/         # 接口层：REST Controller、消息监听器
```

### 依赖方向（严格单向，禁止反向）
```
interfaces → application → domain
                ↓
            infrastructure（实现 application 定义的 port 接口）

跨上下文：只允许依赖对方的 *-api 模块；领域事件通过 Spring 事件总线异步传递，禁止直接调用对方 application 层。
```

### 数据库隔离
按表名前缀分 schema：`id_`、`qa_`、`rep_`、`dis_`，禁止跨前缀 JOIN 和外键引用。

## 后果
- **正面**：
  - 领域层零框架依赖，QuestionTest 等单元测试毫秒级跑完，无需 Spring 容器或数据库。
  - 跨上下文边界由 Maven 依赖图强制，ArchUnit 测试可在 CI 里拦截违规依赖。
  - 龙负责 co-qa domain/application，何负责 co-qa infrastructure/interfaces，两人改不同子模块，merge 冲突最小。
- **负面**：
  - 模块数量多（6×5=30 个 Maven 子模块），IDEA 导入和首次构建较慢。
  - 领域对象和 JPA 实体之间需要手动映射（见 ADR-008），存在少量样板代码。
- **演进**：将来要拆微服务时，Discovery 上下文优先拆出（它是纯下游、只读投影），拆的时候只需要把进程内事件总线换成 MQ，业务代码不动。

## 被否决的替代方案
- **传统三层（controller/service/dao）单模块**：写起来最快，但所有上下文的业务代码混在一起，达不到 DDD 教学目标，也没法做边界强制。
- **按技术层分模块（所有 entity 一个模块、所有 controller 一个模块）**：比三层好一点，但依然是技术视角，换业务时要跨多个模块改代码。
- **每个上下文直接打成独立可部署服务（微服务）**：见 ADR-001，运维成本远超团队能力，16 周课程做不完。
