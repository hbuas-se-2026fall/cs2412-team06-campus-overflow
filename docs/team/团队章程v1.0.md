# CampusOverflow 团队章程 v1.0

## 1. 团队基本信息
- 项目名称：CampusOverflow 校园问答社区
- 课程：软件工程
- 班级：计科2412班
- 团队人数：5人

## 2. 角色分工
| 角色 | 成员 | 职责 |
|------|------|------|
| PO（产品负责人） | 喻向鹏 | 维护Product Backlog、优先级排序、需求验收、协调冲突 |
| SM + Developer（QA） | 王 | 主持Scrum会议、流程改进、质量门禁、测试 |
| Backend Developer | 龙 | 后端核心业务逻辑、领域模型、API实现 |
| Backend Developer | 何 | 数据库、基础设施层、部署脚本 |
| Frontend Developer | 从 | 前端页面、交互、前后端联调 |

> 规则：每个Sprint结束后可投票轮换角色，确保每人都体验不同岗位。

## 3. 团队价值观
1. **代码评审不形式化**：每个PR至少1条实质性意见，不能只点LGTM
2. **小步提交**：功能完成一个就提一个PR，不要攒大代码块
3. **遇到阻塞立刻说**：不要一个人卡半天，在群里喊一声，SM组织快速对齐
4. **文档跟着代码走**：改了接口、改了设计，同步更新文档，不欠账

## 4. 沟通约定
- 沟通工具：微信群
- 每日站会：实验课上同步，每人说三句话：昨天做了什么、今天计划做什么、有什么阻塞
- 会议纪要：SM负责记录，发到群里
- 紧急问题：直接打电话，不要等

## 5. 完成定义（DoD - Definition of Done）
一个任务标记为Done，必须同时满足：
- [ ] 代码写完，能正常运行
- [ ] 单元测试通过，核心聚合覆盖率≥90%
- [ ] 提交PR，至少1人Review通过
- [ ] PR已合并到main分支
- [ ] 相关文档已更新（接口文档、ADR等）

## 6. 分支命名规范
- 功能开发：`feature/功能名`（例：feature/vote）
- 修复bug：`fix/bug描述`（例：fix/login-error）
- 紧急修复：`hotfix/紧急修复描述`

## 7. 提交信息规范
格式：`类型: 简要描述`
- `feat:` 新功能
- `fix:` 修bug
- `docs:` 改文档
- `refactor:` 重构
- `test:` 加测试
- `chore:` 构建/工具相关

## 8. 分支保护规则
- main分支禁止直接push
- 所有代码必须通过PR合并
- PR至少1人Review通过才能合并

## 9. Sprint节奏
| Sprint | 内容 | 周期 |
|--------|------|------|
| Sprint 0 | 团队组建、工具链搭建 | 第1-2周 |
| Sprint 1 | 需求建模、事件风暴、领域设计 | 第3-5周 |
| Sprint 2 | 前后端工程骨架、第一个端到端接口 | 第6-9周 |
| Sprint 3 | 核心特性开发、测试质量门禁 | 第10-13周 |
| Sprint 4 | CI/CD、容器化部署上线 | 第14-15周 |

## 10. 投票与决策
- 技术选型：全员投票，少数服从多数，PO最终拍板
- 任务分配：SM根据每个人负载情况协调
- 争议解决：先两人讨论，谈不拢PO裁决
